ct-translate — Claude Code だけで組む治験翻訳ハーネス

Foundry/Azure 不要。files ＋ サブエージェント ＋ git だけで「用語集準拠 ＋ 逆翻訳投票検証 ＋ 出典紐付け」の治験文書翻訳を回す最小設計。
2026-06-27 ／ 合成ダミーによる方法論デモ（実データ・秘密情報は含まない）

大規模プラットフォーム（PCI / Microsoft Foundry）でやっていた翻訳プロセスを、リポジトリ内のファイルと git に畳んだもの。色は Claude が自動実行 人間・git（HITL＋監査） MD ファイル（用語集・メモリ）

処理フロー

「プラットフォーム」が全部リポジトリ内のファイルと git に畳まれている。git log がそのまま改ざん検知付きの監査台帳になる。

各プロセスの仕組み

  • ⓪ Mode 判定 … SKILL.md の手順を Claude が読んで実行。文書タイプから Mode A/B/C と方向（JA⇄EN）を決める。これが「ハーネス」の本体。
  • ① 用語注入 … 原文の用語を glossary/*.md から grep し、該当語だけ読む（JIT）。AdaptCT の「お手本注入」に相当、インデックス構築は不要。
  • ② 翻訳 … セクションをサブエージェントで並列翻訳。①の訳語を制約として渡す。
  • ③ 逆翻訳で投票検証 … 独立サブエージェントが原言語に逆翻訳し、原文との意味等価を投票。過半で不一致なら棄却。翻訳役と検証役を分ける＝生成と検証の分離。
  • ④ 整合＋loop … 全文で用語のブレを統一。弱い訳は②へ戻し、新規ゼロまで反復。
  • ⑤ HITL 承認 … High 文書は人間が git diff を見て承認。「コミット前レビュー」がそのまま規制の承認ゲート。
  • ⑥ git commit … 確定の瞬間。git log が改ざん検知付きの監査台帳になる（Part 11 を別途作らずに満たす）。
  • ⑦ フライホイール … 確定対訳を memory.md に追記→用語集に昇格。回を追うごとに人手修正率が下がる。

移植と精度の鉄則

この設計の肝：アカウントは自由に変えてよい。モデルは固定し、変えるときは変更管理（リバリデーション）。

変更出力精度への影響
Claude アカウント（個人→会社）／ホスト（PC→サーバ）／API 経由（Anthropic 直 ↔ Foundry ↔ Bedrock、同一モデル）変わらない（鍵・場所が変わるだけ。同一モデルなら実質同等）
モデルそのものを変える（Claude→他、Opus→Haiku）／モデルのバージョンが変わる変わる（モデルは品質の最大の決定要因）

ハーネス（用語集・ガードレール・逆翻訳投票）は精度をモデル非依存の方向に安定させるが、生の流暢さ・ニュアンスはモデル依存が残る。期待値は「同じ訳文が毎回出る」ではなく「品質が毎回担保される」——LLM は同条件でもビット単位では揺れ、用語集＋逆翻訳投票がその揺れを critical な軸で抑える。本番では使用モデルとバージョンを pin し、変更時は 4 段ラダーで再評価する。

「何がどれだけ効くか」を測る — 4 段ラダー実験

同じ原文に層を1つずつ足し、用語集と検証の寄与を数値化する。

段用語集SKILL.md逆翻訳投票確かめること
0 素訳✗✗✗モデル交換そのものの差（基準線）
1 ＋用語集✓✗✗用語の一貫性・指定訳の遵守
2 ＋SKILL✓✓✗プロセス整備（出典・Mode 判定）
3 ＋DW✓✓✓意味欠落・義務弱化の検出

用語集の構築と利用

  • 構築（3経路）：① 顧客指定訳を手入力（P0）／② 確定訳が memory.md→p2-house.md に昇格（自動で太る）／③ 未知語だけ web 参照し取得訳を p3-official.md に追記（キャッシュ）
  • 利用：grep して P0→P1→P2→P3 の先勝ち。層間不一致は ⚠️要確認 で人間へ
  • 原則：毎回 web を引かない。答えはローカルに固定（訳ブレ＝フライホイール破綻を防ぐ）。決定論的に固定すべき情報を確率的経路に乗せない
